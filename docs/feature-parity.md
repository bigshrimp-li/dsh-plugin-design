# 功能对比：本插件 vs 原版 Claude Design

## 先说依据

我没有直接用 Claude Design，下面关于「原版」的判断来自两处**可查证的材料**：

1. **BaoCut 的 `packages/design-runtime/`** —— 它的 README 自述这是 Claude Design 线上发布的最小化 JS 的**逐函数重建**（20,463 个函数，19,111 个完全对上）。所以它的目录结构基本就是原版的功能地图。
2. **BaoCut 内置的两个 skill** —— 提示词层是原版行为的文字描述（格式规则、标注 locator、设计系统挂载方式）。

结论基于这两处的**模块清单与代码组织**，不是基于我用过原版。个别功能我只能从文件名推断用途，下文标了「推断」。

对「本插件」的判断是实测的：都在本仓库的测试里跑过。

---

## 一、总览

| 能力面 | 原版 Claude Design | 本插件 |
|---|---|---|
| **用自然语言做设计** | ✅ 会话里生成 | ✅ 一样 |
| **设计稿格式** | `.dc.html` + `canvas.json` | ✅ **同一个格式**（能装同一套设计系统） |
| **格式校验** | ✅ | ✅ 移过来了 |
| **渲染出图给模型看** | ❌ **明令禁止**渲染/截图 | ✅ **新增**，而且是必做步骤 |
| **可视化编辑器** | ✅ 完整（33 个模块） | ⚠️ 能用，覆盖核心 |
| **元素级结构编辑** | ✅ 增删/换序/换层级/包裹 | ❌ **没有** |
| **矢量/钢笔编辑** | ✅ | ❌ 没有 |
| **PDF 导出** | ✅ 分页、纸张、阅读顺序 | ❌ 只有 HTML |
| **整套设计导出** | ✅ 单文件 HTML / ZIP | ⚠️ 一块画板一份 |
| **标注批注** | ✅ locator + 宿主弹框 | ❌ 没有 |
| **AI 在画布里改（fast-edit）** | ✅ 草稿预览、沙箱 | ❌ 没有 |
| **多人协同** | ✅ 光标、在线状态 | ❌ 没有 |
| **设计系统组件挂载** | ✅ bundle 全局 + 真组件 | ⚠️ skill 支持，运行时路径**未验证** |
| **便签 / 参考线 / 页面** | ✅ | ❌ 没有（格式支持，编辑器不画） |
| **查找替换** | ✅ 高亮 + 滚动揭示 | ❌ 没有 |
| **缩略图 / 版本历史** | ✅ | ❌ 没有 |

一句话：**格式、提示词、校验这三层已经对齐；编辑器这一层只做到「改样式和文字」，原版的编辑能力大约覆盖了三成。**

## 二、本插件多出来的

不是所有差异都是缺口，有两处是本插件更强：

**1. `design_render` —— 模型能看见自己做的东西**

原版把「渲染、截图、打开」写进了**禁止事项**，因为它的编辑器会给人看。DSH 没有编辑器时这条不成立：格式全对但排版一塌糊涂，谁都不知道。所以这里把渲染做成了必做步骤。

实际抓到过：装饰圆弧被色块切断（`viewBox` 写错）、正文最后一行只剩一个词、字体加载后标题自动折行（**排版随网络变**）。这些格式校验一条都查不出来——它们全是「看一眼就知道」的问题。

**2. 工具优先，编辑器可选**

原版的重心是编辑器，agent 是辅助。这里是反过来的：七个工具不依赖编辑器就能跑完「写 → 校验 → 渲染 → 导出」。编辑器是给人补刀用的。对「让 agent 做设计」这个用法，这个重心更合适。

## 三、差距，按「值不值得补」排

### 第一档：用户马上会撞到

| # | 缺什么 | 为什么重要 | 量级 |
|---|---|---|---|
| 1 | **结构编辑**（删除 / 复制 / 插入 / 换序 / 包裹） | 现在想删一个元素只能跟 agent 说。这是编辑器最容易被抱怨的地方 | 大 |
| 2 | **标注回流** | 在画板上框一块、写句话，作为带 locator 的上下文交给 agent。locator 格式 `#<tid>:<path>` 在 skill 里**已经定义好了**，选区我也有——缺的只是「画框 + 写话 + 送进会话」 | 小 |
| 3 | **多选 + 批量改** | 改三个卡片的圆角要改三次 | 中 |
| 4 | **复制粘贴** | 基本预期 | 小 |
| 5 | **重做（redo）** | 现在只有撤销，撤错了回不去 | 小 |
| 6 | **画布平移缩放** | 现在只有「适应 / 100% / 75% / 50%」，大画板不好看局部 | 小 |
| 7 | **便签与参考线** | `canvas.json` 的 `notes` / `guides` 格式本来就支持，编辑器一个都不画 | 小 |
| 8 | **PDF 导出** | 海报、印刷品、多页 deck 都要它 | 中 |
| 9 | **整套设计导成一份** | 现在一块画板一份 HTML；多屏流程想要一个文件装下全部 | 小 |

### 第二档：明显提升，但要动手

| # | 缺什么 | 说明 | 量级 |
|---|---|---|---|
| 10 | **代码视图** | 选中元素后直接看/改它的源码片段，比在属性面板里找字段快 | 小 |
| 11 | **颜色选择器与排版控件** | 现在是纯文本框，输入 `#C2410C` 全凭记性 | 中 |
| 12 | **查找替换** | 跨画板找文字和颜色，带高亮 | 中 |
| 13 | **缩略图** | 设计稿列表现在只有名字 | 小 |
| 14 | **版本历史** | 原版有 `manifest-history`；现在只有单步撤销 | 中 |
| 15 | **设计系统组件挂载** | skill 里写了 `<x-import component-from-global-scope>` 和 bundle 全局，但**这条运行时路径我从没验证过**——很可能有坑 | 中 |
| 16 | **页面（pages）** | `canvas.json` 的 `pages` 支持多页，编辑器只按 `order` 列画板 | 小 |

### 第三档：大工程，建议先不做

| # | 缺什么 | 为什么先不做 |
|---|---|---|
| 17 | **fast-edit：AI 在画布里改** | 原版的旗舰功能——选中元素、描述改法、**草稿预览**、确认后落盘。要沙箱 + 宿主代调模型 + 草稿 UI + 撤销栈。工作量比现有整个编辑器还大 |
| 18 | **多人协同** | 光标、在线状态、协同选中。单人工作流下价值为零 |
| 19 | **矢量/钢笔编辑** | 原版有完整的路径编辑。但用 agent 做设计时，图形基本是 SVG 直接写出来的 |
| 20 | **完整 flex/grid 布局控件** | 属性面板已经把 `display`/`gap`/`flex`/`align-self` 都放出来了，够用 |

## 四、如果只做三件事

**① 结构编辑（第 1 项）** —— 缺口最大、抱怨最多。可以从最小的做起：删除、复制、上下移动一项。这三样覆盖大部分不满。

**② 标注回流（第 2 项）** —— 性价比最高。格式已经定好、选区已经有了，缺的只是一个画框工具和一条「送进会话」的路径。而且它直接回应了这次会话最初的那个问题：**用户说「这个标题再大一点」，agent 只能猜**。

**③ PDF 导出（第 8 项）** —— 现在的导出只能给「看」，不能给「印」。海报和印刷品是明确的使用场景。

---

## 五、说清楚一件事

原版是**一个编辑器，里面长了个 agent**；本插件是**一个 agent，旁边挂了个编辑器**。所以逐项比「编辑器功能」的话，差距会一直存在，而且补齐它等于重写那 33 万行。

更有意义的比法是：**对「让 agent 做设计、人负责验收和微调」这个用法，哪些功能真正被用到？**

按这个标准，第一档那九项就是全部——第三档那些（协同、矢量、fast-edit）在单人和 agent 主导的流程里几乎不会碰。而真正把这条流程撑起来的 `design_render`（模型看得见结果）和严格校验，反而是原版没有或刻意不要的。
