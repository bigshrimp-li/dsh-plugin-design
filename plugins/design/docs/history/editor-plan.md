# 给 DSH 做一个设计稿编辑器：方案

目标：在 DSH 里人工实时改 UI —— 点选、拖动、改样式、改文字，改完 agent 能接着改同一份文件。类似 Claude Design 的编辑体验。

**结论：可行，但不要移植 BaoCut 的编辑器。** 那套是 330k 行、663 个文件的重建代码（而且权利来源不明，见 `NOTICE.md`）。而 DSH 上要做同样的事，**地基已经有一半了** —— 而且这套格式自带两个关键机制，让"轻量编辑器"成为可能。

---

## 一、两个已经就位的关键机制

这两个是整份方案成立的前提，都实测过。

### 1. 运行时已经在每个渲染出来的元素上标了源节点 id

我把 order-flow 的画板跑起来，数了一下 DOM：

```
stamped: 38 个元素带 data-dc-tpl
tpl=1 → <link>      （helmet 里的）
tpl=2 → <style>     （helmet 里的）
tpl=3 → <div>       （画板根元素）
...
```

而格式文档里对 `tid` 的定义是：

> 把 `<x-dc>` 开始标签与最后一个 `</x-dc>` 之间的片段里每个**元素**按文档顺序编号（深度优先），从 0 开始

对照一下：`<helmet>` 是 0，它的 `<link>` 是 1、`<style>` 是 2，根 `<div>` 是 3 —— **`data-dc-tpl` 就是 `tid`**。

这意味着"用户点了这个按钮" → "要改源码里的哪个元素"**不需要任何推断**，运行时直接告诉你。这是做直接操作编辑器最难的一环，而它是免费的。

### 2. 编辑模型就是改行内 style —— 也就是改文本

格式里写着：

> properties panel 编辑的是行内 `style="…"`

所以"所见即所得地调样式"落到源码上就是：**找到第 N 个元素，替换它的 `style` 属性**。不需要 AST、不需要框架、不需要把一个 React 组件树序列化回源码。

而"找第 N 个元素"这件事，`canvas-check.ts` 里已经有一个 HTML tokenizer 了（`TAG` 正则 + `attrList` 属性解析），按同样的深度优先顺序走一遍就是 `tid`。

**结论：编辑器的写入端，核心大约 150 行。**

### 3. 顺带一提：选区定位的格式也已经定义好了

`skills/design/references/view-state.md` 里已经规定了标注块的模样（`#<tid>:<path>` 的 locator、label 怎么截断、文件名怎么做百分号编码），连正则都写好了。也就是说**标注通道的数据格式不需要重新设计**，只需要实现 UI 那一侧。

│    GET  /<board>.dc.html     → 画板 + 运行时 + 编辑器桥      │

**复用清单** —— 这一层几乎不用新造：

| 已有 | 用在哪 |
|---|---|
| `vendor/support.js` | 在 iframe 里把画板挂起来（这一步已经能跑） |
| `src/render.ts` 的服务端 | 编辑器服务的骨架（加几个端点即可） |
| `src/check/canvas-check.ts` 的 tokenizer | tid → 源码位置 |
| `design_check` | 每次改完自检，防止编辑器产出不合法的画板 |
| `view-state.md` 的 locator 格式 | 选区 → 交给 agent 的上下文 |
| `ctx.betterSidebar.registerTab()` | 面板落在哪（已装插件暴露的服务，28+ 插件在用） |
| `--dsw-alias-*` 主题 token | 面板跟着宿主明暗主题走 |

DSH 侧的接入点实测确认：

```ts
export const inject = ['betterSidebar']
export function apply(ctx: Context) {
  ctx.effect(() => ctx.betterSidebar.registerTab({
    id: 'design-editor', title: 'Design',
    component: ({ scope }) => <DesignEditor sessionId={scope.sessionId} />,
  }))
}
```

## 三、分期

### P0 · 地基（已完成）

运行时、本地服务、渲染、导出、tid 标记、`design_check`。`design_render` 已经是"起服务 + 跑浏览器 + 收结果"的完整回路。

### P1 · 选区与标注（2–4 天）—— **建议从这里开始**

**不做编辑**，只做"点哪说哪"：

- 侧边栏一个面板，`<iframe>` 里是画板（服务端在渲染时多注入一段编辑器桥）
- 鼠标悬停高亮、点击选中，桥把 `{tid, tag, text, box, computedStyle}` 发回父窗口
- 面板显示选中的是什么（"Main.dc.html › text「Ethiopia Guji」"）
- 「交给 agent」把这段作为上下文塞进会话

**为什么先做这个**：它一个人就消掉了现在最大的摩擦 —— 用户说"这个标题再大一点"，agent 只能猜。有了选区，请求变成 `Main.dc.html #3:1/0 text "Ethiopia Guji"`，**零歧义**。这是 `view-state.md` 里那套 locator 存在的理由，只是 BaoCut 靠它的编辑器产出，这里我们自己产。

而且它逼着把 `tid → 源码位置` 这条链先建起来、测通 —— 那是 P2 的前置，早晚要做。

成本主要在 client 插件的骨架和 postMessage 协议，**服务端几行、桥约 150 行**。

### P2 · 直接改（1–2 周）

- 属性面板绑到选中节点的行内样式：宽高、内外边距、gap、颜色、字号、字重、圆角、边框
- 拖动 / 缩放改位置与尺寸
- 原地改文字（文字节点直接 `contenteditable`，失焦写回源码）
- 撤销栈（存源文件快照）
- 每次写完：`design_check` → SSE 通知 iframe 重载 → 属性面板重新读值

**范围要卡死**：只改**选中元素自己的行内样式**。理由见下面「硬骨头」第一条。

### P3 · 结构调整（数周）

加/删/换序元素、wrap in flex/grid、复制一份。到这一步才开始真正复杂 —— BaoCut 的编辑器里最大块的代码（`canvas/` 59k 行、`editor/` 99k 行）基本都在处理这类操作的历史、约束与撤销。

建议先把 P2 用一阵，看真实需求再定 P3 做多少。

### 不做

- **移植 BaoCut 的 design-runtime**。330k 行、需要实现 7 个 `designHost` 能力、还依赖它的 slides 服务层；更要紧的是那套代码是 Claude Design 线上 JS 的重建，**权利不来自 BaoCut**（`NOTICE.md` §3）。自己写编辑器反而干净。
- **完整对齐它的功能**。它的多人在线、评论、导出 PDF、缩略图、快速编辑 Worker，对"人工实时改 UI"这个目标都不是必需的。

## 四、硬骨头（诚实清单）

**1. 不是每个视觉属性都能落到行内 style。**
改父元素的 `gap` 会动到所有子元素；`font-family` 从根元素继承下来，选中一个 `<span>` 改字号，旁边同样继承的兄弟不受影响，但改字体族就会。**规则**：只让改选中元素**自己声明**的属性；继承来的、推导出来的值**只读展示**（标注"继承自根元素"）。不守这条，面板上改一个值会动到用户没选的地方。

**2. 行内样式这条纪律是承重的，不能破坏。**
格式要求静态 theme token **直接写在行内**（"这样流式传入时就能画出来"），`<helmet><style>` 只放页面基础样式。编辑器如果把属性提升到 `<style>` 里，会破坏流式渲染。**写入必须留在行内。**

**3. 布局是 flex/grid，不是绝对定位 —— 拖动没有干净的映射。**
把一块从左边拖到右边，在 flex 里该改的是顺序，不是坐标。三条路：
  (a) 拖动只用来**换序**、以及调 gap/padding/尺寸 —— 安全，但不像"自由拖动"
  (b) 提供"转为绝对定位"，同时冻结兄弟元素（BaoCut 的原版就是这么做的：*"观看者也可以把某一项从两者中拖出来：这时编辑器会冻结其余兄弟元素和父元素的尺寸"*）
  (c) 拖动只改 `align-self` / `flex-grow` 这类"在流内移动"的属性

建议 (a) 打底 + (b) 作为显式动作。

**4. 有两个写者，撤销的语义是模糊的。**
人和 agent 改同一个文件。朴素规则：写入前**当场重读**（skill 里本来就是这么要求的），文件在自己加载后被改过就**拒绝写并提示刷新**；编辑器自己的撤销只回退自己的改动。真正的合并（CRDT/OT）不值得做 —— 用"重读 + 拒绝"就够了。

**5. 没渲染出来的东西点不到。**
`<sc-if>` 为假的分支、`<sc-for>` 的模板内部、被 `<dc-import>` 引进来但在别的文件里的节点 —— 都不在 DOM 里或不属于本文件。需要：
  - `<sc-for>`：一个 template node 渲染 N 份，选中一份就是选中模板节点（改一处 = 改全部）。这是**正确**行为，BaoCut 也是这样（"`<sc-for>` 里的一个元素不管渲染多少次都是一个 entry"）
  - `<dc-import>`：点进去选中的是**引入方文件里的 `<dc-import>` 元素**，不是被引入文件的内部（同上）
  - `<sc-if>` 假分支：需要一个"源码视图"兜底，或者接受点不到

**6. 文字编辑和 `{{hole}}` 冲突。**
如果那段文字是 `{{title}}` 绑定的，原地改文字应该改**哪里**？改 prop 的 default？还是改成字面文字（等于断开绑定）？格式里明确说 copy 就该是字面文字、不做成 prop —— 所以默认行为是"改字面文字"，但**绑定了 hole 的节点要拒绝原地编辑**，提示用户改成改 prop。这条不定清楚，用户会无意中把数据绑定改坏。

## 五、代码量级与现实感

| | 自己写 | 移植 BaoCut |
|---|---|---|
| P1 选区标注 | ~400 行 | — |
| P2 直接改 | ~2,000 行 | — |
| P3 结构调整 | ~3,000–6,000 行 | — |
| **合计到 P2 可用** | **~2,500 行** | 330,000 行 + 7 个宿主能力 + slides 服务层 |

到 P2 就是"点选 + 改样式 + 改文字 + 撤销"的可用编辑器了 —— 覆盖"人工实时改 UI"的绝大多数真实需求。P3 是锦上添花。

## 六、建议的第一步

**先做 P1，别急着做编辑。**

理由：它是独立的、能立刻验证价值的最小切片，而且它产出的 `tid → 源码位置` 映射正是 P2 的地基。做完 P1 你会知道两件事：

1. 选区定位准不准（`data-dc-tpl` 在 `<sc-for>`、`<dc-import>`、`<sc-if>` 这几种情况下是不是还可靠）
2. 用户真正想改的多半是什么（大概率和预想的不一样，直接决定 P2 该先做哪几个属性）

具体交付：一个侧边栏 tab，里面是 iframe 画板；点一下，会话里就多一条"用户选中了 X"的上下文；「交给 agent」按钮把选区连同当前源片段一起发出去。**不改任何文件。**
