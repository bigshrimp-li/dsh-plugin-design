# Bot 上下文策略与 UI 测试报告

**结论：本轮没有达到替换现用策略条件的候选方案。** 区间记忆方案在固定开发集通过了更多规则断言，但没有稳定提高缓存命中率或降低成本。四种方案都复现了同一条用户请求产生两条正式笔记的问题。优先处理任务分派的动作边界、工具回执大小和上下文预算，再比较记忆策略，收益更明确。

本轮只做评测。没有修改产品实现、安装配置、模型设置、UI 原型或真实用户业务数据。候选策略只存在于独立的实验副本；交互检查使用合成数据。报告日期为 2026-10-28。

**已确认模型用量：185,414,252 token；另有 4 次请求未返回用量，无法给出完全精确的总 token。保守费用估算为 99.07 元，包含未知请求预留，低于 100 元上限。** 完整口径见“用量与费用”。

## 测试对象与方法

测试对象是 OKR Schedule 3.1.0 的实际 Bot、领域工具、SQLite 持久化和 DSH 会话装配。使用已安装的 DSH 0.2.1-rc.3、Electron Node 24.21.0、真实 AgentLoop 与 scoped tools。模型路由为 `opencode-go/deepseek-v4.1-flash`，有返回型号的请求均报告 `deepseek-v4.1-flash`。

模型采用低推理档，业务调用输出上限为 4,096 token。相同场景使用相同初始数据和用户输入，四种策略各重复三次；每次运行有独立空间、数据库和任务身份。短轨迹并发为 4，长轨迹并发为 8。并发批次的耗时不能当作单用户在 DSH 界面中的等待时间。

每次真实请求都记录输入、输出、缓存字段与费用。业务正确性依据 SQLite、工具回执和已发布答案判断，不以“模型说保存成功”为依据。测试在私聊中拒绝不支持的类型；不会把请求转给其他空间。群入口按内容拆分，再交给各空间处理。

判定分三层：

- **底线规则：** 不重复正式写入、不越过来源边界、不复活删除记忆、不让取消后的旧运行提交。
- **质量：** 正确理解材料与指代、任务继续或新建符合预期、记忆有来源且在正确范围使用、每条应答请求有用户可见答复。
- **效率：** 完整输入与未缓存输入、缓存命中率、输出、调用放大量、发布耗时和总费用。高缓存命中率不能抵消无用历史增长。

原方案提出：先通过底线规则，再要求质量无明显回退；成本或延迟至少改善 15%，另一项不恶化超过 10%。本轮四种策略已经出现底线失败，因此后续变体与长轨迹作为诊断，不作为上线验收。

## 实际比较的四种策略

SP 指系统提示词；状态块指 Host 提供的空间能力、来源与任务状态。下面描述实际运行的实验配置，不把原讨论稿中的完整设想算作已实现能力。

| 策略 | SP 与状态 | 历史与任务分段 | 记忆与工具 |
|---|---|---|---|
| 当前基线 | 现有主 Agent 负责分派，子 Agent 用 `task_report` 发布；状态提供空间、类型、工具和记忆维度索引 | 用空间累计字符数触发统一换段；没有分别约束主、子模型完整输入 | 长期偏好通过 `memory_propose` 写入、`memory_recall` 查询；查询依赖维度相等和连续子串匹配 |
| 保留任务历史 | 增补“每条用户输入都必须分派并发布”，明确连续讲解与笔记整理默认续接 | 主、子会话分别在约 8,000 输入 token 后换段；主会话恢复最近 12 条用户/答案事件；子任务保留首条、最近 8 条用户引用、必要材料、末次答案和交接信息 | 明确记忆证据枚举；保留原有召回方式；更正需关联被替代记忆 |
| 区间与有效记忆 | 继承上一方案，增加临时约定与当前有效记忆快照 | 独立换段；子任务最近用户引用减为 4 条，主会话仍为最近 12 条事件 | 增加带来源和有效范围的 `interval_update/recall`；装入最多 5 条长期记忆和 5 条区间约定；快照仅在首次或内容变化时追加 |
| 按需检索重建 | 继承区间方案，并要求遇到指代时读取授权原文 | 每次新投递重建物理会话；主会话保留最近 4 条事件和 3 条词法匹配，子任务保留首条、最近 2 条和 3 条相关用户引用 | 词法排序，无向量模型；仍有有效记忆与区间工具，允许按引用读取历史 |

三个候选都同时改了派发提示、记忆工具枚举和上下文策略。因此，下面比较的是组合方案；不能把“偏好写入成功”全部归因于区间记忆。工具枚举单因素消融没有完成。

实验的 8,000 token 是投递间的换段触发值，不是模型每次请求的硬上限。一个投递内部的工具循环仍可能超出该值。区间记忆只覆盖任务内或明确时间范围的约定；没有完整实现跨任务学习进度、经历自动归纳和大规模记忆筛选。

开发集的自适应换段场景因旧夹具选错被延长的任务，部分轨迹扩展到 30 轮。该场景保留诊断证据，但从固定输入成本主比较中移除。群用例原夹具错误携带了私有空间绑定；回复丢失夹具最初未覆盖 `space_complete` 保存路径。这两类已修正运行器并重跑，没有修改被测产品。

语义评审对策略名称做了隐藏，但仍使用同一型号模型，不属于独立模型交叉验证。固定输入主比较中，98/132 条有可解析的语义评审或执行助手复核；其余 34 条不补零，也不按通过计算。部分评审耗尽输出额度而没有给出 JSON。执行助手还纠正了“建议草稿等于正式事项”“同一事项的 body 与 fields 等于两次保存”等误判。没有完成外部人工盲审及原计划的全部抽审覆盖，因此不发布完整语义成功率或每成功任务成本排名。

### 上下文预算没有覆盖真实请求

两个完成 100 轮的基线场景中，主会话均没有换段：连续追问单次最大输入 160,156 token，任务交错单次最大输入 285,880 token。插件累计字符分别只有 26,617 和 23,128，尚未达到 32,000 的换段阈值。实际模型上下文已经包含大量状态事件、主 Agent 输出和工具往返。

原因可定位到 [字符累计与换段判断](/Users/bytedance/worskpace/dsh-plugin-design/plugins/okr-schedule/src/host/bot.js:483)：目前的计数没有覆盖完整编码请求。缓存命中较高，并不代表上下文预算正确或长期成本受控。

长材料场景还有独立问题：子 Agent 的 `task_get` 会再次返回完整 `operationReceipts`。实测一次回执中，这部分序列化后超过 35 万字符；查询过的材料又被带回任务状态。基线已观察到 308,448 token 的单次输入，区间方案也观察到 143,306 token。换段发生在投递间，不能限制同一次工具循环中的大结果。[任务查询实现](/Users/bytedance/worskpace/dsh-plugin-design/plugins/okr-schedule/src/host/bot.js:237)

后续应分别约束模型请求预算与工具结果预算：状态只保留回执摘要和引用；正文按页或按引用读取。业务权威数据仍保留完整，不需要为了省上下文删减正式记录。该建议尚未实现，也没有算作本轮收益。

## 主要问题与复现

### 同一请求被两个任务重复执行

优先级：高。四种策略均复现。

1. 在学习空间提交“保存一条缓存定义笔记，并记住以后讲概念先举例”的组合请求。
2. 主 Agent 分别建立保存任务和偏好任务。
3. 两个子任务拿到同一条完整用户消息，各自读取到“保存笔记”的指令。
4. 两个子任务分别保存了正文相同、ID 不同的正式笔记。

重复保存发生在记忆维护重试之前。单一投递重试的幂等已在“回复丢失”场景通过，但不能防止两个合法子任务分别完成同一个业务动作。任务标题也不能构成可执行的权限限制。

建议在派发时绑定具体动作与授权内容片段，并为一个逻辑写入保留跨子任务可识别的身份。记忆任务只处理偏好，不重新解释整条消息中的业务写入。只增加“不要重复”的 SP 不足以构成可靠约束。

### 基线有处理结果，但没有用户可见答复

优先级：高。固定输入主比较中，基线有 4 条用户输入没有可见答复，涉及纯偏好设置、删除后的查询和不支持的记录请求。

主 Agent 被规定不直接发布业务回答，但模型仍可能直接说出自然语言后结束，没有调用 `task_create/task_send`。后台自然语言不等于空间里已经回复。三个候选通过显式派发要求消除了本次样本中的缺答复，但仍需要 Host 对“收到用户消息却没有派发或发布”提供可观测的失败状态。

### 记忆写入与召回的工具契约不清楚

优先级：中。

- `memory_propose` 实现只接受三个证据枚举，提供给模型的 schema 却只声明字符串。基线实际传入了其他拼法，收到 `not_activated`；三次明确长期偏好都没有持久化。[工具声明](/Users/bytedance/worskpace/dsh-plugin-design/plugins/okr-schedule/src/host/bot.js:425)
- 维度命名可能在 `preference` 与“解释偏好”之间变化；召回又要求维度完全一致。多关键词查询也可能无法连续命中已有文本，返回空结果。[召回过滤](/Users/bytedance/worskpace/dsh-plugin-design/plugins/okr-schedule/src/host/bot.js:365)
- “答案先举例”不能单独证明记忆召回成功。模型可能仍从授权聊天历史读到偏好。本轮明确区分了持久化、工具召回和答案遵循。
- 本篇临时约定结束后，基线与保留历史方案有未恢复长期偏好的样本。区间工具提供了明确范围，但本轮记忆库很小，尚不能证明大量无关记忆下的筛选效果。

后续应统一维度标识、把枚举写入工具 schema，并分别测抽取准确率、召回命中、有效范围与最终遵循。区间方案的自动快照目前没有过滤零相关分，也没有独立 token 硬预算；不宜直接扩大到大量记忆。

### 任务粒度仍不稳定

优先级：中。“讲解 FIFO/LRU → 追问第二种 → 保存刚才讲解”经常在保存阶段另建任务；已有讲解任务仍是可续接的 `delivered`。保存通常正确，但连续任务被拆开，后续选择任务和恢复上下文更复杂。

建议继续保留已经对齐的粒度：同一材料、同一交付目标的讲解、补充与整理可续接；可独立交付的新目标另建；已结案只建立关联任务。需要增加可观测的分派理由与稳定的动作范围，而不是按每条消息或主题词机械切分。

## UI 合理性

UI 采用当前 DSH 插件客户端和原有样式评估，没有使用浅色旧原型。真实 DSH 只做查看；可能写数据的步骤在独立合成空间执行。评估按 [Product Design Audit 技能](/Users/bytedance/.codex/plugins/cache/openai-curated-remote/product-design/0.1.56/skills/audit/SKILL.md) 的使用动线和证据检查方式进行。

| 问题 | 实际操作与结果 | 影响与建议 |
|---|---|---|
| 切换空间沿用旧草稿，优先级高 | 在学习空间点击已结案任务“继续”，切到运动空间。回复引用消失，但学习内容仍在运动输入框 | 用户可能误投递。按空间保存输入草稿，显示接收空间和引用摘要。本次未发送该草稿，没有发生跨空间写入 |
| 原表单补齐后留下待整理，优先级高 | 添加跑步，距离留空后保存；提示待整理。仍在原表单补入 5 再保存，正式记录出现，旧待整理仍提示缺距离 | 用户不清楚是否完成，后续再补可能重复。首次返回待整理后，原表单应关联同一材料；直接保存，不增加撤销流程 |
| 聊天区域与回答格式，优先级中 | 桌面聊天固定在窄栏，长表格和 Markdown 标记以普通文本出现；技术 ID 占据回复 | 核心解释难读。支持展开聊天、渲染常用格式，业务结果优先显示可读名称，技术引用折叠 |
| 任务续接反馈，优先级中 | 已结案任务仍有“继续”“取消”；继续只预填旧目标，提示“正在回复选定消息”，焦点留在按钮 | 难判断将续接还是新建关联任务。按钮随状态变化，展示任务名、引用片段和实际处理结果 |
| 记忆来源难核对，优先级中 | 来源展开后是 `message:…` JSON。修改可正常保存，但仍显示旧来源标识 | 用户无法核对原句或手动修订。展示来源原文、时间、作用空间及修改标记 |
| 首屏入口过多，优先级中 | 九个同级功能入口；任务列表位于全部聊天之后 | 记录、对话与当前任务不突出。调整信息层级，保留高级入口；无需恢复拖拽积木 |
| 窄窗口与术语，优先级低至中 | 760×850 视口导航横向溢出，聊天位于记录之后；缺项提示暴露 `distance` | 改为“距离（公里）”等用户字段名。聊天首屏可见性需改善；未完整验证滚动可达性，不能据此说聊天不可用 |

已有合理设计也得到验证：群聊与私聊标题有区别；正式空记录区说明保存后才显示；无模型时发送被禁用；记录和消息可进入轨迹；记忆编辑对话框能自动聚焦、Enter 提交并立即更新。

## 结论适用范围

- 没有发现可直接切换的完整策略。区间方案值得保留为后续实验方向，但尚未证明整体性价比更好；按次重建也没有证明更便宜。
- 存储与上下文隔离的通过项，只代表本轮特定数据和来源用例通过，不代表所有安全场景已穷尽。
- 新变体仅各一次，长轨迹也各一次；不提供精确的泛化成功率或显著性胜出声明。短轨迹与长轨迹并发不同，不混合比较延迟。
- 临时记忆跨天通过测试事件推进逻辑有效期；没有修改操作系统或 Provider 时钟，也没有测 Provider 缓存过期时间。
- 没有完成受控前缀缓存专项、工具枚举单因素消融和全部语义重评。底线失败与 100 元预算使本轮没有继续执行完整验收矩阵。
- 没有覆盖图片输入、完整经历记忆自动提取、大规模召回 precision/recall、真实用户长期使用或所有任务冷却/休眠时间边界。图片是前期产品诉求，但当前插件实施范围明确未包含，属于范围缺口，不作为本轮回归失败。
- UI 未完成真实模型等待、错误重试与取消状态的端到端交互检查，也未进行屏幕阅读器和完整无障碍审计。页面回放与真实模型服务测试分别报告，不能互相替代。
