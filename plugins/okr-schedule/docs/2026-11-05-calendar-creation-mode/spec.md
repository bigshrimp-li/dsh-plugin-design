## 实现与验证

3.2.0 将已登记的「目标日程」侧栏接到全局月历，同一工作区内可打开单个空间和全屏创造模式。「记录与 Bot 工作台」保留早期方案、显式迁移、旧群聊及轨迹入口。若要手动重放，可在插件目录运行 `node scripts/preview.mjs --calendar`，用当天的三个合成空间操作，退出服务会清理临时数据。

工作区使用随插件分发的本地页面资源，正式读取和提交通过同源 Host 接口。根安装器和分发包沿用原包名、Loader ID 和数据根目录。

| 验收动线 | 核对结果 |
|---|---|
| 选择目标和时间 | 上海 11 月 5 日只选英语时，当天安排有 19:30 的词汇复测。加选阅读后出现 20:30 的阅读与摘记。月格第三项进入当日日视图，重叠事项各自可点。 |
| 会话切换、引用与删除 | 输入后新建会话，返回取回原输入。点击一次建议只产生一轮问答。引用超过两条可展开。删除英语后，跨 O 的旧合计提示失效，阅读引用仍能打开。 |
| 创造模式与正式提交 | 在同一英语草稿改首项时间、周汇总和手工说明。暂离时正式空间为零。点击确认后，目标、成对 K/R 与两项日程可从两个页面读回。跨入口可取消、续回或放弃原草稿。 |

### 原型对照

以本目录 HTML 原型与三张参考图为准。使用同宽浏览器分别打开实现和关闭标注的原型，断言顶栏、目标栏、日历卡与助手的宽度、横向位置误差小于 2 CSS 像素。另用合成数据截图逐项核对助手引用分组、固定 O/K/R、月度收支卡片和创造编辑区。五步标注及三个演示档的重置仅在离线原型走查。截图在核对后清理。

### 复现入口

1. 在仓库根运行 `npm run check` 和 `npm test`。
2. 在插件目录运行 `npm run test:browser`。Chrome 加载真实插件页面，通过临时 HTTP 与 SQLite 保存。需要固定模型输出以验交互时使用合成传输，另有纯离线的原型测试。
3. 运行 `npm run test:host` 核对实际 DSH AgentLoop、工具权限和 SQLite Worker，再运行 `npm run test:host:browser`。后者从隔离 DSH Web profile 的实际侧栏验证进入、返回、重进、宽窄屏与五档缩放。
4. 从插件源码目录运行 `node scripts/calendar-model-probe.mjs`，通过隔离的 DSH 会话向已配置的 Provider 发送合成目标。宿主默认路由须可用。仅模型连接配置来自现有 profile，正式业务及会话放在临时目录。
5. 运行 `npm pack --dry-run` 与 `node ../../scripts/install-profile-probe.mjs`，核对所需页面、宿主入口、指令文件和 CLI 均在分发包内，以及独立安装、重复安装、共存与备份。该安装探测使用临时 profile。个人桌面的后续复验与数据清理单独记录在下文。

### 问题处理

- 在临时目录中打断删除，复现了目录已经移走、旧索引仍待清理的状态。首页现在会列出待清理的原 ID，修复索引后可从原入口完成。两个 Worker 竞争初始化 WAL 时出现过短暂占用，增加初始化重试后连续 50 次竞争创建和修订通过。
- 核对记账原型时发现，表示发生时刻的账目曾多计 1 分钟计划。现在入账只保存实际发生时刻，计划分钟和忙闲统计排除该占位时长。账目仍可从日历与月卡打开。
- 真实 Provider 曾返回无法解析的 JSON。助手使用相同只读权限重试一次，仍失败时保留原草稿并显示实际服务状态。输入法选字、重复投递、过期回执和删除后的历史引用均有专门断言。

### macOS 原生桌面复验与本机清理

在 macOS 上正常退出旧实例，打开已安装的 DeepSeek Harness 0.2.1-rc.5。沿用现有 desktop profile 和模型配置。从侧栏进入 `dsh-app://app/okr-space/ui/index.html`，使用合成目标进行复验。

- 英语空间从模型拟案开始，将 19:30 调整到 20:00，暂离时日历仍为零个目标，续回 v2 后点击确认才生成正式空间。周、日视图和助手引用均可打开同一事项。
- 日历保存 16 / 20 的执行结果后，空间助手依据该记录起草 R，手工核对并保存。单独标记与撤销实现均保留同一条 R。原生保存面板可分别导出两份 Markdown，两份下载文件与已确认空间生成的原文逐字节相同。
- 记账空间实际登记 120 元餐饮与 30 元交通。月卡显示 150 元，筛选后的月卡与助手均显示餐饮 120 元。只改长期规则的调整草稿通过按钮应用到原空间，两笔交易均保留。
- 复现了跨口径问题：同一句话提及「保持当前筛选不变」与「查 11 月全部支出，不限类别」时，助手错误地继续用餐饮筛选取数。
- 修正后，在重启的同一桌面、同一空间、同一历史会话和相同筛选下，逐字重发原问题，得到人民币 150.00 元并引用两笔明细。反向问「当前视图全部支出是多少」返回 120.00 元，仅引用餐饮。两次查询均未改变页面筛选。
- 核对时还发现，模型曾称账目金额「统一折算」，实际工具没有汇率。账本取数现明确返回原币种口径。在同次账本查询的答复声称换算，或混合币种需要分列时，用同轮可核对的合计与引用呈现。加入美元的合成交易后，原生月卡与重启后的桌面助手分别列出 CNY 150.00、USD 10.00，三条来源均可展开。单币种视图、双向统计、提及汇率的规则调整另有回归断言。
- 修订后根 `npm run check`、`npm test` 通过。目标日程 102/102，`npm run test:browser` 为 9/9，另复验了隔离宿主默认模型。个人桌面使用真实已配置的模型，没有复用合成模型答复。
